## Context

Поточний стан: у репозиторії відсутній датафрейм-движок, сумісний за підходом із Polars Python, але орієнтований на Go runtime. Для MVP v0.1 потрібен фундамент, який одночасно покриває eager/lazy API, columnar модель даних, базовий оптимізатор та IO-інтеграції (CSV/JSON/Parquet/Arrow) без надмірної архітектурної складності.

Ключові обмеження:
- Неймінг публічних операцій має відповідати Polars Python семантиці.
- Потрібна продуктивність для великих обсягів даних через векторизацію та паралелізм.
- API має залишатися type-safe і передбачуваним для Go-користувачів.

## Goals / Non-Goals

**Goals:**
- Побудувати єдине execution-ядро для eager і lazy шляхів.
- Визначити публічний API `DataFrame`, `LazyFrame`, `Expr`, `IO` з chainable методами.
- Реалізувати базовий rule-based оптимізатор: predicate pushdown, projection pruning, constant folding.
- Додати форматні адаптери CSV/JSON/Parquet та Arrow-інтероп для табличного обміну.
- Додати SQL frontend для базового класу запитів без дублювання execution-логіки.

**Non-Goals:**
- Cost-based optimizer, adaptive runtime re-optimization.
- Розподілене виконання на кілька вузлів.
- Window functions, nested/list/struct типи, advanced join режими.
- Повний feature parity із Polars у межах v0.1.

## Decisions

1. Єдине ядро виконання для eager і lazy
- Рішення: eager виклики транслюються у короткий логічний план і виконуються тим самим фізичним рушієм, що й lazy.
- Чому: мінімізує дублювання операторів і розбіжності результатів.
- Альтернатива: окремий eager executor. Відхилено через більші витрати підтримки.

2. Columnar storage з chunked серіями
- Рішення: серії зберігаються по колонках із чанками фіксованого діапазону, null bitmap винесений окремо.
- Чому: краще для векторних обчислень, кеш-локальності та паралелізації.
- Альтернатива: row-oriented layout. Відхилено через нижчу ефективність для аналітичних запитів.

3. Публічний API в `pkg/polars`, ядро в окремих пакетах
- Рішення: користувацький фасад відокремлений від внутрішніх планувальників і операторів.
- Чому: стабільний API-контракт та гнучка еволюція внутрішньої реалізації.
- Альтернатива: exposing internal packages напряму. Відхилено через ризик ламати сумісність.

4. Polars-семантика назв у Go-формі
- Рішення: операції називаються за Polars Python (`select`, `filter`, `group_by`, `with_columns`), але у Go-експорті як `Select`, `Filter`, `GroupBy`, `WithColumns`.
- Чому: сумісність ментальної моделі для користувачів Polars та відповідність Go-конвенціям.
- Альтернатива: чисто Go-орієнтований неймінг без мапінгу на Polars. Відхилено через втрату сумісності API-очікувань.

5. Rule-based optimizer для v0.1
- Рішення: впровадити тільки детерміновані правила без статистичної моделі вартості.
- Чому: дає відчутний приріст продуктивності з мінімальною складністю.
- Альтернатива: одразу CBO. Відхилено як надмірно складне для MVP.

6. SQL як frontend до того самого logical plan
- Рішення: SQL parser/binder/planner генерує ті самі `Expr` та logical nodes, що й API.
- Чому: одна поведінка, одна система оптимізації, менше розходжень.
- Альтернатива: окремий SQL engine. Відхилено через дублювання.

## Risks / Trade-offs

- [Високе споживання памʼяті на wide-таблицях] → Впровадити chunk sizing, buffer pooling і обмеження на materialization у lazy collect.
- [GC паузи при інтенсивних алокаціях] → Використовувати reuse буферів, уникати зайвих проміжних колонок, бенчмарки на алокації.
- [Непаритет між SQL та API виразами] → Обовʼязкова нормалізація в один Expr AST та golden-тести планів.
- [Складність Parquet/Arrow інтеграції] → Спочатку обмежений профіль типів для v0.1 та чітка матриця підтримки.
- [Ризик API-нестабільності] → Чіткий MVP-контракт і policy зворотної сумісності до v0.2.
